# План доработок PR-Market

Текущий порядок работ согласован с заказчиком 2026-09-23. Приоритет определяется риском: достоверность данных и деньги, затем ключевые сценарии, настройки и расширения. Этот план является рабочим; завершенность пунктов проверяется по критерию в конце, а не по наличию экрана или API.

## Этап 1. Достоверные данные

- Подключить финансы заказчика к `/balance` и `/transactions`: одинаковые суммы в шапке, панели и финансовом разделе.
- Пересчитать панель паблишера из реальных заказов и проводок: реальные счетчики, сроки и суммы.
- Подключить финансы паблишера: начислено, ожидает приемки, доступно и удержано рассчитываются сервером.
- Исправить счетчик очереди администратора: материалы и споры считаются из базы.
- Согласовать модель комиссии: интерфейс соответствует фактическому удержанию при завершении заказа.

Критерий: любая сумма совпадает во всех кабинетах и после перезагрузки.

## Этап 2. Жалобы и споры

- Передавать выбранный `orderId` на все страницы спора.
- Заменить демонстрационные `C-020`, суммы и доказательства данными заказа.
- Создавать жалобу через серверный переход заказа в статус спора.
- Хранить причину, ссылку, дату и вложения.
- Добавить серверный ответ паблишера и его доказательства.
- Реализовать дополнение и отзыв жалобы.
- Оставить четыре административных решения: возврат, полная выплата, частичная выплата, закрытие без санкций.
- Показывать обеим сторонам решение и финансовый результат.

Критерий: полный сценарий проходит тремя ролями, сохраняется после перезагрузки и не допускает повторной выплаты.

## Этап 3. Финансовые операции

- Добавить реквизиты паблишера и статус их проверки.
- Создать сущность заявки на выплату.
- Подключить список и карточку выплат в админке.
- Записывать подтверждение, возврат и отклонение в аудит.
- Добавить реальные ручные корректировки баланса с обязательным основанием.
- Формировать закрывающие документы из завершенных заказов.
- Подключить финансовые выгрузки.

Банковское перечисление можно подключить позднее. До этого внутренний процесс выплаты должен работать без фиктивного статуса перечисления.

Текущий статус (2026-09-28): проверка реквизитов, заявки на выплату, администраторские решения, корректировки баланса и CSV-выгрузки подключены к базе и аудиту. Для завершенных заказов заказчик может сформировать неизменяемый проект акта от «Аксиомы» и скачать PDF; финансовая таблица показывает завершенные размещения и статус проекта акта. Проект акта не считается подписанным закрывающим документом. Способ подписания и выдачи окончательного акта еще не согласован; до этого пункт о закрывающих документах остается частично выполненным.

## Этап 4. Основные карточки

- Передавать ID рекламодателя при открытии карточки.
- Добавить получение и редактирование рекламодателя через API.
- Убрать фиктивное подтверждение внешней проверки.
- Подключить фильтры каталога: тип, тематика, цена, срок.
- Подключить фильтры заказов паблишера: статус, площадка, дедлайн.
- Проверить все переходы из панелей, уведомлений и связанных сущностей.

Текущий статус (2026-09-28): карточка рекламодателя открывается по ID через защищенный API и сохраняет правки; новые заказы записывают ID рекламодателя в снимок, старые сопоставляются по ИНН. Ложное подтверждение внешней проверки убрано, неподключенные административные действия не показывают успех. Фильтры каталога и заказов паблишера работают по загруженным из API данным; срок каталога учитывает выбранный формат. Уведомления о заказах ведут к конкретному заказу соответствующей роли. Браузерные проверки выполнены на desktop и mobile. Настоящая проверка/блокировка рекламодателя администратором остается задачей этапа 5; автоматического внешнего сервиса сейчас нет.

## Этап 5. Административные функции

- Заявки паблишеров: таблица, API, решение, история.
- Создание кабинета паблишера после одобрения заявки.
- Блокировка пользователя и отзыв его сеансов.
- Проверка и блокировка рекламодателя.
- Реальные карточки пользователей, заказов, площадок и рекламодателей.
- Сохранение комиссии, SLA и сроков ответа по спору.
- Убрать локальные сообщения об успехе: подтверждение показывать только после ответа сервера.

## Этап 6. Настройки пользователей

- Профиль компании или редакции.
- Юридические и банковские реквизиты.
- Команда, роли и приглашения.
- Настройки уведомлений.
- Прочитанные и непрочитанные уведомления.
- 2FA.
- API-доступ паблишера.

Сначала сохраняются настройки и права в базе. Почтовая и Telegram-доставка подключаются отдельным шагом.

## Этап 7. Репутационный мониторинг

- Добавить обработчик очереди на PostgreSQL без Redis.
- Подключить источники утвержденной архитектуры.
- Сохранять исходные результаты каждого провайдера.
- Извлекать текст только для отобранных по сниппету материалов.
- Выполнять семантический анализ через OpenRouter.
- Формировать материалы, выдачу, AI-сниппеты, тематики и негатив из результатов сканирования.
- Рассчитывать динамику только после появления сопоставимых снимков.
- Заменить все демонстрационные показатели сохраненными результатами сканирования.

## Этап 8. Эксплуатационная полнота

- Серверная пагинация и поиск.
- SLA и контроль дедлайнов.
- Фоновые уведомления.
- Вложения в чатах и поддержке.
- Прочтение сообщений.
- Внутренние комментарии и назначение ответственного.
- Журнал ошибок фоновых заданий и повторный запуск.

## Критерий готовности

Для каждого этапа действие записывается в базу, переживает перезагрузку, отображается другой уполномоченной роли, попадает в аудит и отклоняется для чужого аккаунта.
